# 对 Liz 的 agent 聊天面 / Product Studio 的对照笔记

只根据本案例已经看见的公开证据来写。不改任何产品代码。grok.com 是闭源产品，不进 agentic UI 的轮子池。

## 值得带回讨论的

1. **聊天即产品时，侧栏可以缺席。** 访客首页把整张画布留给问候 + composer，登录和注册是右上角的次要 chrome。这和 `templates/ui-patterns/ai-workspace-surfaces.md` 的「主对象在中间、Agent 在右侧 rail、不要让聊天占满工作区」并不冲突——那份合同针对的是记录/文档工作台。Grok 的主对象就是对话。Product Studio / Shelf Radar 若做的是「研究或提案对象还在」，不要抄这张满幅聊天；若做的是「从一句提示开始的空白会话」，这张空态更近。

2. **技能进 composer，而不是另开一排工具栏。** Writing / 网页搜索 / 邮箱日历以芯片的形式嵌在输入条里，下面的建议列表整组跟着换。模式（至少能看到 Fast）收在同一条的右端下拉，不占顶栏。若 Studio 要在同一条输入里切换「写报告 / 搜网 / 画图」，这比顶部 model 切换条更省垂直空间。本轮没打开下拉，不知道还有没有 Thinking 等项，不要假装见过。

3. **问候是会动、会本地化的。** 英文问候会在 “agenda” 与 “your mind” 之间轮换（WebFetch 抓到动画中间态），其它语言整句替换。占位符有时仍是英文，或中英/德英混排（技能名 Writing 出现在德文界面里）。做多语言空态时，动画文案和芯片名要一起纳入翻译，不要只译标题。

4. **临时会话在皮肤层有位置。** CSS 有 `--incognito-*`，文本抽取里有「这条聊天不进历史、不用来训练」的声明。如果 Studio 要做不进项目记录的试探对话，应在空态就说清楚，而不是发完再补。

5. **兄弟面可以换 composer 形态，不必共用一条输入条。** Imagine 的 composer 更厚，把画幅、质量、时长、媒体类型放进同一张卡片，下面用 masonry 示例而不是问句列表。Chat 保持细 pill。这是「同一产品、按任务换输入壳」，不是换一套导航。

6. **登录墙不是整页墙。** 未登录就能看到完整的聊天空态；登录是右上角出口，带 `return_to`。对「先让人感到产品，再请他留下」的公开面有用。未验证发出去的第一条会不会被中途拦住。

## 不要学的

- 不要把 x.ai 营销卡上的 “Thought for 2.8s” 和工具芯片当成 grok.com 应用里已实测的流式规范；那是营销插图。
- 不要学 cookie 横幅正文留英文、按钮却本地化的裂缝。
- 不要把公开 JS 里的 `/rest/...` 字面量当成可接的后端合同，更不要去打。
- 不要把 15.5rem 侧栏或 425/525/650 字重直接搬进自己的 DESIGN.md——那是对方的尺，只说明「访客态可以没有侧栏」和「字重可以不走 400/500/700」。

## 仍缺的对照

登录后的会话栏、工作区切换（官方商务文档说在左下角）、thinking/流式、Projects 与 Automations 的真实空态，都还没有第一手画面。要补，只能在授权会话里只读看，不能用这个案例里的静态路径去猜交互。
